# 愿景保真度审计

> 对照对象：用户最初提出的架构构想（MiOpIIk = M/O/T 三层 + 鱼骨上下文树 + 前后台分离）。
> 判据：不是「代码里有没有这个函数」，而是「**实际运行时，用户体验是否还是那句话描述的样子**」。
> 审计时间：2026-11-04。状态：✅ 成立 ｜ 🟡 部分成立 ｜ ❌ 未成立。

## 一句话愿景

> **持续对话与异步行动相互独立，却又能够自然地协作；任务从对话中产生，执行在后台推进，结果经过整理后重新融入对话，而用户的思路始终是交互的中心。**

## 逐条对照

### 1. 「M 是持续与用户交流的主体，不是接到模糊指令就长程执行」

- 现状：✅
- 证据：`host/prompt.js` 章程把「派发前自检：能复述目标且说出完成的样子」写死；`host/contract.js` 六要素缺一即拒绝派发（实测缺样例/边界时被拒并给出缺失清单）。
- 说明：M 仍持有 bash 等执行工具（DSH 默认），结构上并未强制窄工具面。

### 2. 「M 始终关注用户，不为复杂任务抛下用户；长程任务交给后台」

- 现状：🟡
- 证据：`ink_dispatch` → `ctx.subagents` 以 `delivery: 'caller'` 启动，结果回 Ink 不回对话；O 的会话与 M 的会话完全分离（实测 J-1…J-5 五个 Operator 均在自己的会话里跑）。
- 缺口：**M 的工具面没有被结构强制收窄**。SPEC §1.8 要求「长程执行能力不在 Mind 手上」，目前只靠章程。`enforceMindToolSurface` 仍是登记项（会破坏现有使用，需用户明确同意才做）。

### 3. 「O 调度、T 执行、可递归」

- 现状：✅（合并后）
- 证据：`host/operator.js` 用 `ctx.subagents` 派发，子 agent 默认是完整 agent，可再派子 agent；O/T 合并为 Operator 是既定结论（SPEC §7）。

### 4. 「鱼骨式上下文树：主干是对话，分支从对话节点长出、可递归、适时汇回主干」

- 现状：🟡 **本轮从「没有」变成「有了肋骨」**
- 已做（2026-11-04 第二轮）：`branches.jsonl` + `ink_branch`（open / summary / merge / abandon）+ `ink_dispatch` 的 `branch` 绑定；分支记 `forkedAtTurn`（从对话第几轮长出）与事件序号；L3 末尾一行「鱼骨分支：B-1 …（2 个任务（1 完成 / 1 在跑），从第 7 轮分叉）」；汇回主干产出一条带分支指针的预览；抽屉新增「鱼骨分支」。
- 仍缺：**分支上下文切片**（分支只带一句话摘要，没有独立的上下文窗口）；**分支可递归**（分支下再造分支）；分支之间互不可见。
- 影响（剩余）：用户说「上次那个方案」时 Mind 能按分支指代了，但仍不能「进分支里看」；仍画不出真正的鱼骨图。

### 5. 「用户提想法时，M 一边回复一边判断是否值得执行；区分探索/成形/行动；不过度主动也不事事下令」

- 现状：✅（以另一种方式）
- 证据：结论是「不设意图分类器」，改为**可验收性自检**（能否一句话复述目标 + 说出完成的样子）；正式派发留复述，草稿态免门槛（`ink_draft` + 草稿 7 天老化）。
- 说明：这与最初「后台判断」不同——判断权留在 Mind 自己，Ink 不做意图判断。这是后续讨论的明确结论，不算失真。

### 6. 「M 前台与后台分离：共享必要状态，不共享推理细节，两条时间线并行」

- 现状：🟡
- 证据：Ink 是独立于对话常驻的后台（事件驱动 + 定时老化 + 守夜），与 M 的时间线确实并行（实测：我写代码时 Operator 在跑、Ink 在编译）。
- 缺口：没有真正的「M-fg / M-bg」两个推理实例；Ink 承担的是**编译与记账**，不是第二个 M。这与「双 M 否定」的结论一致，但意味着「后台分析意图」这一原始设想被替换成了「Mind 自己判断 + Ink 异步编译」。

### 7. 「O 的结果不原样插入主对话」

- 现状：🟡 → ✅（本轮修复）
- 本轮修的真实失真：降级预览的 claim 曾经直接搬 Operator 报告开头（`O-J-2 有结果了：Ciallo~~ **交付报告**…`），这正是愿景禁止的「原样插入」。现在 claim 只用契约目标裁剪（`clip(goal, 26)`），原文只进 `detail`（要展开才看）。
- 另修：`hold` 的 claim 不再直接搬 Operator 的英文原问题。
- 缺：编译成功时是好的（一句话 + 问题），但 `detail` 里仍存 Operator 全文——这是有意的（无损存储），不违反愿景（M 不读就不会进对话）。

### 8. 「渐进式任务可见性：M 只掌握目标、关键进度、结论，需要时再深入」

- 现状：✅
- 证据：L3 只给一行预览（claim + 开环 + 问题）；展开靠 `ink_inbox open` 取 detail；Operator 过程细节从未进入 M 的上下文（实测 J-1 的 11 步过程我一句都没看到）。

### 9. 「自然打断与注意力恢复：无关信息暂存、相关信息自然融入、重要发现影响方案、用户切话题后能恢复」

- 现状：🟡
- 已做：收件箱分层（T0–T3）+ 每轮最多 3 条 + 同一开环一条待读；epoch 推进让旧预览降级；开环 2 天休眠 / 7 天折叠；**本轮新增对话节奏信号**（最近三条长度、确认型回复数、停顿分钟数、有无活跃开环）——只给信号不给阈值，让 Mind 自己判断间隙。
- 缺口：没有自动话题切换检测（epoch 靠 Mind 手动 `ink_epoch advance`）；「恢复原先思路」只有开环 + 简报，没有 utterance 级的断点指针。

### 10. 「用户不必关注任务调度、执行状态和技术细节」

- 现状：🟡（产品面 ✅，**对话面 ❌**）
- 产品面：客户端只有输入框下方一个「后台」入口（有任务才带数字）+ 抽屉三 tab；没有导航栏、没有任务面板（实测截图）。
- **对话面（元失真）**：我这几轮给你的回复，本身就是「batch 编号 + 测试数 + commit 哈希」的工程进度报告。这正是愿景里明确说「用户不该被迫关注」的东西。做架构的人和被架构服务的用户，在同一次对话里分裂了。
  - 这是本审计最重要的一条发现：**机制对了，但扮演 Mind 的那个家伙还在像项目经理说话。**

### 11. 「用户思路始终是交互的中心」

- 现状：🟡
- 已做：展示是「提议不是倾倒」（预览结尾是疑问句，用户只需一个字）；闸门只要求判断不要求修理。
- 缺：用户主动岔开话题后「回到原处」仍靠 Mind 自觉；没有机制保证。

## 承诺（写给下一次开场的自己）

- 你说「在做吗」→ 一句话 + 一个具体的东西，不要表格。
- 你不问细节 → 不给哈希、不给测试数、不列批次。
- 有坏消息 → 先说结论，再说影响，最后才说原因。

## 结论

架构层面：**愿景的主体（对话与行动解耦、结果经整理回流、渐进可见、闸门只问判断）成立，且已在真实 GUI 里跑通。**
结构上：鱼骨现在有主干 + 肋骨（分叉点、任务挂载、汇回主干），但**还没有分支自己的上下文**——分支是「一个有名字和一句话摘要的挂载点」，不是「一段可以独立展开的上下文」。这是下一阶段的主任务。
最大行为缺口：**Mind 的说话方式**（第 10 条），没有技术手段能强制，只能靠这条承诺。
